# API 变更说明 v0.2.1

| 项 | 内容 |
|---|---|
| 版本 | v0.2.1 |
| 日期 | 2026-11-16 |
| 兼容级别 | A（Additive）+ B（Behavioral，仅视图失效粒度） |
| 影响 crate | `tslib-core`、`tslib-audio-aec3`、`tslib-jni` |
| 影响绑定 | Rust / Java |
| 关联 spec | 无 |

---

## 1. 快速迁移清单

### 必须改（C/D）

无。本版没有签名破坏。

### 建议改（B）

| 旧行为 | 新行为 | 建议 |
|---|---|---|
| 任何事件（聊天、poke、文件进度、talk 翻转）都会让视图 revision +1 并发 `view_changed` | 只有 users/channels/server info 真正变化时才 bump | 若曾把「收到 `view_changed`」当成「有新事件」用，请改为监听具体事件。轮询名册的嵌入方（如 Android）应改用 `Client::view_revision()` 提前短路 |
| `User::is_talking` 随快照更新 | 快照里的该字段可能滞后；实时状态请消费 `TalkStatusStart` / `TalkStatusStop` | 需要「谁在说话」的 UI 走 talk 事件，不要读名册快照里的标志 |
| `Aec3EchoEngine::new` 固定 NS=HIGH | 新增 `with_noise_suppression(..., level)`；`new` 仍是 HIGH | 无感知；想降档时用新构造器 |

### 无需改（A）

- 新增 `Client::view_revision()`；旧方法全部保留。
- 新增 `NoiseSuppressionLevel` 枚举与 `Aec3EchoEngine::with_noise_suppression`。
- 新增 Java `OpusDecoder`（仅解码器）与 `Client.getViewRevision()`、
  `EchoCanceller` 的可选 NS 档位构造器。
- JNI 新增符号；旧符号一个未动。

## 2. 方法签名变更

| ID | 模块/方法 | 旧签名 | 新签名 | 级别 | 绑定影响 |
|---|---|---|---|---|---|
| API-101 | `tslib-core::Client` | 无 | `fn view_revision(&self) -> u64` | A | Java `Client.getViewRevision(): long` |
| API-102 | `tslib-audio-aec3::Aec3EchoEngine` | `fn new(rate, frame, tail)` | 保留；新增 `fn with_noise_suppression(rate, frame, level)` | A | Java `EchoCanceller(sampleRate, frameSamples, tailSamples, nsLevel)` 重载 |

### 绑定层新增 JNI 符号

| 符号 | 说明 |
|---|---|
| `Java_dev_tslib_Client_nativeGetViewRevision` | `Client.getViewRevision()` |
| `Java_dev_tslib_OpusDecoder_nativeCreate` | 仅创建解码器（不建编码器） |
| `Java_dev_tslib_OpusDecoder_nativeDestroy` | 释放 |
| `Java_dev_tslib_OpusDecoder_nativeDecode` | 解码一包（可选 FEC） |
| `Java_dev_tslib_OpusDecoder_nativeDecodePlc` | 丢包掩盖 |
| `Java_dev_tslib_EchoCanceller_nativeCreateWithNoiseSuppression` | 指定 NS 档位创建 |

旧的 `Java_dev_tslib_EchoCanceller_nativeCreate` 签名与行为完全不变。

## 3. 行为语义变更（签名不变也要写）

| ID | API/事件 | 旧行为 | 新行为 | 影响 | 迁移 |
|---|---|---|---|---|---|
| API-110 | `Event::ViewChanged` / `ViewReady` 的触发条件 | pump 内只要产生任意事件就 bump revision | 仅当用户/频道/服务器信息变更时 bump | 事件条数变少；名册快照不再因聊天消息刷新 | 轮询方改用 `view_revision()` 判断；依赖「每事件必刷新」的代码见下文 |
| API-111 | `User::is_talking` | 随 talk 事件写入快照，下一次 `users()` 可见 | 仍会写入，但**不再单独触发**视图失效 | 快照里的标志可能滞后于实时 | 实时说话状态用 talk 事件 |
| API-112 | `Aec3EchoEngine::reset()` | 重建时固定用 HIGH | 重建时沿用创建时选的档位 | 无（默认即 HIGH） | — |

### API-110 的收益与代价

收益：在 100–200 人的服务器上，一条聊天消息不再导致下游把整份名册通过
JNI 重新序列化一次；talk 翻转（音频速率）彻底不再触发名册重建——这是本版
的主要性能目标。

代价：`view_changed` 不再是「有事件发生」的信号。仓库内受影响的唯一嵌入方
是 Android App，其 `TsClient` 已改为「revision 变化才刷新 + 2 秒兜底」，
兜底用 `view_revision()` 比较后决定是否序列化。

## 4. 绑定层变更

### 4.1 Java / JNI

| 项 | 旧 | 新 | 迁移 |
|---|---|---|---|
| `Client.getViewRevision` | 不存在 | 新增 | 可选 |
| `OpusDecoder` | 不存在 | 新增（仅解码器） | 接收侧可用它替代 `OpusCodec`，省掉多余编码器 |
| `EchoCanceller` NS 档位 | 固定 HIGH | 新增 4 参构造器（0=low…3=very high），3 参构造器行为不变 | 可选 |

`OpusDecoder` 与 `OpusCodec` 的 `decode`/`decodePlc` 语义一致（同样的
`frame_size_samples × channels` 输出长度、同样的 FEC 回退）。

### 4.2 Python / C

本版未改动 `tslib-python`、`tslib-ffi`。
